# 先研究地方，再组织旅行

这是新城市采编的起点。既定路线是时间与范围的约束，不是城市介绍的资料来源。不要先把每日 stops 批量映射成区域文章，再给每段补“先看、再走、留时间”。

交付的是值得阅读、选择充足的完整旅行读物，不是每章几句的行程摘要。读者明确希望内容详实时，应充分展开正文；简洁用来删空话和重复，不能用来删解释、例子、比较和真实候选。大图、折叠列表和短摘要不能替代展开后的正文。

动笔前按 directory-standard.md 确定目的地档位、地点与餐饮候选范围，写入已有 directory-plan.json；先列这座城需要研究的主题和地区，再搜集资料。不要先写主线上的十来个地点，再把它们的实际数量填成目标。照片没有找到时继续研究文字资料，不能因此缩减地点和餐厅。

## 1. 先回答城市问题，暂不填正文 JSON

先用官方文化、历史、城市、博物馆或地方研究资料了解目的地，而不仅是景点票务、交通和餐厅页面。把查证笔记写在工作台 `research.md`，以这些问题组织：

- 这是什么地方？地理与城市形态是什么关系，读者如何理解整座城市的空间？
- 它怎样形成今天的面貌？挑对理解现场最有解释力的历史过程，不堆年代表，也不把地点的建成年份当作完整历史。
- 今天的人怎样生活？选择有依据的社区、工作、信仰、饮食或文化活动，解释可观察的表现与差异。

每个问题记录来源、核对日期、支持的事实、可以写出的解释和未确定之处。无需统一条数；缺资料就继续查，不用路线安排或旅行建议替代答案。自然目的地的形成可讲地质与生态，人文与生活按实际存在的内容写，不捏造帝国史或城市街区。

三问是审阅范围，不是三个段落的提纲，更不是每问只找一条事实。研究笔记应保留本城的选题展开：重要背景、它如何形成、与另一片区或另一时期有什么不同、具体能看到什么。发现一句结论还需要解释时继续研究。城市尺度大的地方需要呈现内部差异；不能由一个市场代表全部日常生活，或由一条街的观察代替整座城的文化介绍。

## 2. 先写一篇能独立阅读的城市介绍

在 research.md 后写完整的城市介绍草稿，再拆进 portrait。它应能作为旅行杂志的开篇独立成立：先介绍地方，再解释来历与今天的生活。段落靠事实与关系衔接，不靠“第一天、第二天”衔接。来源支持事实，也要支持因果；并列出现的食物与建筑不能擅自写成同一段历史的产物。

按文章主题组织小节，不按验收题号分三段。每个重要论点向下写清：到底是什么、为何形成这种面貌、用哪些具体事物说明、不同地区或群体是否存在差别。选择适合主题的展开方式，不强制每段套同一四步句式。正文允许连续多段；JSON 中用双换行保留段落，不把全文压成一张卡的一段说明。

校准例：只写“宽大道和窄巷来自不同年代”，接一座建筑的名称，仍是一条导语。采编需要继续查清改造前后的空间变化、动因、保留下来的街区差异及可观察的证据，再写成能理解来龙去脉的小节。城市介绍还应让初访者知道这座地方在更大地域中的位置、独特吸引力和今天的生活，不能只剩几处建筑的视觉关系。这里是研究方向，不是无需查证即可抄用的城市事实。

读完草稿，暂时隐藏所有交通、日次、酒店和提醒：剩下的部分是否仍能让没去过的人认识这座城市？用固定审阅问题检查，答不出就回研究阶段。不要等排版完成再靠补句子修复。

## 3. 再研究区域与专题，最后串回路线

区域按真实地理与生活差异划分，可以与旅行日多对多对应；“抵达”“返程”“第几天”不是地区。区域先讲空间、社会生活及具体观察，文化专题深入对象、来历和观看线索，餐饮讲食物与点法，购物讲当地品类与选择。城市、区域、专题是不同阅读层次，不要求重复同一段历史或同一条路线。

这些内容完成后，再匹配已有路线、开放窗口、餐次、交通与备选。已有路线不合理时记录具体冲突，按用户授权范围修正；不能为迎合旧日程编造营业事实。旅行模式从这些已核对的资料中选择现场需要的介绍、走法与条件，不能只复制导航和提醒，也不搬整篇城市文章。

专题也不能停在摘要：文化要给具体对象、作品或细节及其理解线索；购物要有当地值得选的品类、实际可比较的店与取舍；餐饮要讲口味、菜式、点法，并给不同地区和消费情境的真实分店。某个店查不到就继续找可核实的选择，不用“附近找一家”“按菜单”“看当天情况”填完栏目。餐饮分类的调整必须来自当地情况，不能因只查了两家店就删掉其余推荐角色。

先把正文、地点、餐饮、逐日餐窗与备选做成完整的文字采编稿，运行 `python <技能目录>/scripts/audit_coverage.py <工作台>` 并试读这一稿，再集中做摄影、地图和页面制作。内部阶段不需要新增用户确认。后期不能因素材或排版耗时把已经研究的正文缩成摘要，或删候选来赶交付；确有取舍要回到读者需要与实际适用条件。

## 4. 验收由职责决定问题，不由成稿挑问题

运行 `python <技能目录>/scripts/audit_editorial_release.py <工作台> --init` 得到固定问题。城市的身份、形成、生活分别作答，不能换成“怎样坐车”；各区域与每天旅行模式也有固定问题。答案只能来自实际页面，摘录应支持完整论点，只有地名或半句不能证明解释完成。题目不适合某目的地时，回答其适用边界和对应事实，不擅自把题目换成容易的问题。

程序核对固定问题、覆盖、当前文件与摘录存在；这不是语义判卷。执行者须在另一遍阅读中逐项判断“答案有没有回答题目、摘录够不够支撑答案、来源是否支持事实、实际页面是否可见”。不能以自己的 ready 标记为结论。不要写完原稿立刻从中挑一句自动生成 ready 记录。正式构建前完成这遍审阅；发现问题回正文或研究，不只改审阅记录。

这遍阅读要主动找缺口：陌生读者读到每个结论，是否仍需要追问“为什么、具体是什么、差别在哪”？保留有帮助的追问并补足答案；不是只找一句沾题目的话。对照研究选题检查是否漏掉重要主题，对照片区与餐次检查是否确有选择。摘录存在、三个题目都有答案，仍可能只是薄提纲。试跑若低于目录或餐饮覆盖标准，继续完善或如实判定失败，不能改称“核心通过”后宣布技能整体验证完成。

先 `build.py --preview` 看桌面与手机，再回读旅行模式所有日期，最后执行正式构建。详细证据格式与受影响测试见 release-verification.md。没有字数评分，篇幅由解释的完整程度决定；大图和排版继续保留。

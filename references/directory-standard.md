# 地点库规模、覆盖与照片

地点库是旅途中可替换、可查找的选择集合。以目的地规模、空间分布、停留天数和兴趣决定数量；主线不需要走完所有地点。先确定片区与体验覆盖，再用数量检查是否单薄。

## 完整新刊的规划规模

以下为去重后的有效地点数量，不含未确认酒店、泛称“机场”、休息时段及重复品牌入口。

| 目的地性质 | 1–3 天 | 4–7 天 | 8–12 天 |
|---|---:|---:|---:|
| 多中心大都市，文化／购物／餐饮丰富 | 30–45 | 55–80 | 75–110 |
| 中型城市或紧凑文化城市 | 20–30 | 35–55 | 50–70 |
| 海岛、海岸或分散度假区 | 15–25 | 30–50 | 45–65 |
| 小城、乡镇或自然目的地 | 12–20 | 20–35 | 30–45 |
| 多城组合 | 按各城停留分别估算，合并后去重；跨城交通点单列，不计入观光地点数量。 |||

以上区间是完整新刊的采编规划基线；下限用于阻止候选池未完成时交付，上限不限制已核实的有用选择。主题旅行、重复到访、无障碍或度假慢住可依据用户实际需求调整，记录已有用户要求，而不是自行请求或推定缩减授权。不能因为制作耗时、查图困难、模型上下文或先写了很少的地点而下调；“不凑数”是要求继续找到有差异的真实选择。东京、巴黎等多中心大都市六天采用 55–80 处，主线可以轻松，库内选择仍需充分。

`cityType` 使用 `metropolis`（多中心大都市）、`city`（中型城市）、`island`（海岛/分散度假）、`small`（小城/自然）；`tripDays` 对应实际日数。多城用 `multi-city` 及 `segments: [{cityType, days}]` 分段累加，超过12天也分段规划。`targetRange` 从上表确定，不填实际数量。确有用户缩小范围的要求时，`scopeOverride` 记录 `userRequest` 原话、`reason`、调整后的 `targetRange` 与 `diningTargetRange`；人工核对原话真实且适用。包餐船程、偏远目的地无对外餐饮等客观条件也可用 `basis: verified-availability`、`sources` 和 `reason` 记录已查证限制，不能把未查到资料说成当地没有；餐饮范围可据此为 `[0,0]`。旧 `scaleException` 的一句说明不再豁免正式交付。

有效地点只计可独立选择的游览、餐饮、购物、休息等真实地点。机场、普通车站、未定酒店锚点、重复分店记录不计入基线。可用 `directoryRole: transport/lodging/placeholder` 标明用途；确认不可访问的场所标 `availability: closed`，只作历史背景的标 `directoryRole: context`，均不计入可用规模；名称不同但同一地址/门店也需去重，不能拆条凑数。

## 餐饮候选的规模与用途

餐饮在总地点库内计数，不另造一套重复地点。使用真实餐饮类别（美食、餐饮、咖啡、甜品等）或 `directoryRole: meal`；普通景点、商店和整个市场不能冒充餐厅。按有效分店去重，四类不要求均分。

| 目的地性质 | 1–3 天 | 4–7 天 | 8–12 天 |
|---|---:|---:|---:|
| 多中心大都市 | 6–10 | 16–24 | 24–36 |
| 中型城市 | 4–8 | 10–16 | 16–24 |
| 海岛／分散度假区 | 4–8 | 8–14 | 14–20 |
| 小城／自然目的地 | 3–6 | 6–10 | 10–16 |

将对应范围写入 `diningTargetRange`。这是让读者有选择的研究范围，不要求都吃到，也不允许复制品牌不同写法来充数。先覆盖主要游玩片区的正餐及其同区替代，再加入值得专程吃、当地特色、日常连锁与咖啡甜品的差异化选择。目的地确实不适用某分类时在 `diningCategoryNotes` 写该类别的研究结论；真实候选总量与实际餐次仍需覆盖，不能把所有角色压成两家店。

在同一计划的 `mealCoverage` 记录餐窗到已有候选的映射，例如 `"d2":{"meals":{"lunch":["a","b"],"dinner":["c","d"]}}`。这些 ID 必须同时存在于当天 `dining` 和 `restaurant_groups`；每个适用餐窗至少有一个可行选择及一个关闭/客满时可用的替代。若实际只有唯一餐厅，`alternativeNotes` 按餐窗写明查证结果与自备餐等可行处理，不虚构第二家。餐次键用 `breakfast/lunch/dinner/snack`。中间完整游览日考虑午、晚餐，首尾日写实际餐窗；首尾也是完整游览时标 `dayType: full`，不能按数组位置免除吃饭；没有用餐条件或已安排包餐时用 `reason`（整日）或 `notApplicable:{lunch:具体原因}` 留依据，不能用“自理”或“附近解决”作不适用理由。可以同店适用多个餐窗，但逐一核对厨房服务、位置与绕行代价，不能把全城店单复制给每天。

mealCoverage 是编辑核对索引，当前旅行模式不会自动渲染这个对象。必须把餐窗和包餐等适用条件写进当天实际可见的站点提示或餐饮候选 `fit`/`note`，并实页核查；仅有索引不算完成。映射不代替读者内容：餐饮详情写菜品、口味与点法、预算口径、分店地址和营业条件；旅行模式实际显示餐窗与当日适配。数量达标仍需人工逐片区、逐餐窗走读。缺图采用可靠文字卡，不因此删去餐厅。

逐餐试读还要把主选设为关闭或客满，走一次替代方案。若备选需要下山、跨河、换乘或折返，就交代实际改线和移动时间，并复核下一站预约；不能只列两家店便认为餐窗成立。无需把所有备选编成另一份完整行程，只补受影响的那一段。

正式构建强制运行 `coverage_release.py`（技能侧同入口 `scripts/audit_coverage.py`），未完成覆盖只能预览。旧工作台升级时同步构建接线；目录照片工具 `audit_directory.py` 另查主体、缺图理由和图片文件，照片检查不替代覆盖检查。

## 内容覆盖

- 主线中的地点全部进入库，主要游玩片区都有餐饮、休息与室内／雨天替代；不适用的自然区说明原因。
- 大都市应体现城市地标、历史文化、当代生活、不同价位的具体餐厅、咖啡甜品、购物与用户重点兴趣。海岛按海岸、聚落、自然体验、餐饮与转场补给检查；小城重视真实可用性，不强塞大都市品牌。
- 备选说明适合替换哪一天、哪一段，需要多少时间及是否跨区。远离主线的值得专程去的地点写清替换半天或一天；不暗示顺路。
- 一座商场及楼内值得单独决策的店可以分别收录，但不能把同一处的中文名、英文名、入口、楼层拆成多条凑数量。
- 地点需有准确名称、分店、类别、片区、位置或地址、停留建议、推荐理由、现场注意与来源。`url` 可以是官方、可靠资料或地图搜索入口，并建议标注 `urlKind`；没有官网无需编造官网。地图链接只帮助定位，变动事实仍需来源核查。字段见 [编写约定](authoring-contract.md)。

## 配图与布局

- 地点库的识别照片必须是这个地点，具体餐厅须匹配分店。区域照片仅可用于本身就是街区的条目。阿美横丁图片不能放在上野公园卡片，即使二者在同一片区。
- `place-photos.json` 每条记录 `subjectPlaceId`、`role`（venue/interior/product/area）、`page`、`src`、`caption`、`reviewed`。餐品图明确标餐品，品牌标识不能算地点实景；area 仅用于 `content.json` 中明确 `identityScope: "area"` 的街区条目。具体门店不能靠改 scope 接受错误图。照片候选获取与断点缓存见 [照片管线](photo-pipeline.md)。
- 主线地标与主要街区优先配齐真实图；整个地点库目标不少于 80% 有准确照片。主要地点缺图或低于目标时继续换可靠来源，仍未取得时为具体地点记录原因，使用完整文字卡，交付说明实际覆盖。绝不拿错误照片补比例。
- 新图实际查看，能批量用联系表审阅，疑似错误的单独放大。HTTP 200、图片可解码、同一旅游网站或 OG 标签都不能证明照片身份正确。餐厅 logo、授权提示图、地图 403/Blocked/API-key 图片均不算可用素材。
- 地点库使用稳定的照片＋文字行布局，桌面和手机均显式定义列。不得按当前筛选结果的第几个条目自动变为大图特写。图、文字、来源和操作不能互相覆盖或横向溢出；无图卡不保留空白图片占位。

运行 `python scripts/audit_directory.py <工作台>`，再在实际浏览器验证有图／无图混排、区域筛选、长店名与手机窄屏。程序检查不能替代照片身份与地图画面的实看。

报告的 `pendingPhotoExceptions` 给出待登记地点 ID 和空理由，`pendingPhotoNames` 给出名称；核对实际查找结果后填写，再合并到计划的 `photoExceptions`。不会自动把未找过的图登记为已研究。覆盖率只计算通过文件与身份检查的图片记录。分页改动使用 60/100 地点及 320/390/1440 视口回归，不靠缩小触控区塞满所有页码。
